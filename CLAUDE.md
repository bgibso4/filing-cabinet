# Filing Cabinet — Project Guide

> Formerly the working title "DocuScan" (taken). The repo folder is still `docuscan`.

A private, Photos-style library just for personal documents (IDs, receipts, notes, cards, forms). It scans with Apple's document camera, understands scans on-device with Vision, auto-files them into smart collections, and cleans itself up over time. The pitch is **organized + self-cleaning + private**, not "a scanner."

Personal tool first; possible App Store release later.

---

## Where we are

**Phase: design.** There is no app code yet.

- Design spec: `docs/superpowers/specs/2026-07-12-docuscan-design.md` (draft; open questions in §15).
- We work **mock-driven**: flow diagrams → high-fidelity mocks → interactive mocks (Claude Design), *then* code. Product questions such as the collection set, the cleanup flow, and the home screen are settled in the mocks, not guessed in code.
- Process is Superpowers: brainstorming → spec → plan → TDD → verification. Don't write app code until there's an approved implementation plan.

## Platform & stack

- **Target iOS 27; iOS 26 is the hard minimum** (`RecognizeDocumentsRequest` needs 26). Prefer iOS 27 APIs where they're better, behind availability checks only if we decide to keep supporting 26.
- iPhone only for the MVP. SwiftUI, SwiftData (CloudKit-ready model), VisionKit (`VNDocumentCameraViewController`) for capture, Vision (`RecognizeDocumentsRequest`) for OCR + entities.
- Xcode project is generated by **XcodeGen** from `project.yml` (the `ios` worktree bootstrap runs `xcodegen generate`). Never hand-edit or commit a stale `.xcodeproj`; regenerate after adding/removing files.

---

## Engineering bar

Same bar as Baseline: correct, modular, extensible, obvious to the next engineer.

- **Four units with narrow interfaces:** Capture → Understanding → Classification → Library. Understanding and Classification are pure and unit-tested; Library owns persistence, files, thumbnails, and the cleanup engine.
- **Open/closed where the spec says so:** new cleanup rule types are a new `CleanupTrigger` case plus an evaluator and a registry entry. Don't add a growing `switch` in the engine.
- **One primary type per file.** Views render and route intent; logic lives in view models, services, or pure helpers. Depend on protocols and inject collaborators instead of reaching for singletons.
- **Memory is the real engineering:** originals are HEIC on disk, the DB holds references only, and the grid renders ~400px thumbnails decoded with ImageIO. Never decode full-res in a grid cell.
- No `print()`; use `os.Logger`. Don't swallow errors with `try?` when the caller needs to know.
